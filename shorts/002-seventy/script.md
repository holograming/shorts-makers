## ① 70%의 벽
- 해설 (15초): 이 현상에 이름을 붙인 사람이 있다. 펀치라인은 화자 목소리로.
- **이름 카드 (5초, 0:25 소개 카드에서 옮김):** Addy Osmani — Google Chrome 개발자 경험 팀, 『Beyond Vibe Coding』 저자 · 2025-11 Zed 대담. 원본 첫 3초 동안 화면 왼쪽 아래에 이름 띠로 남긴다(화면을 가리지 않는 띠 영역에).
- **원본 C1 · 04:49.2–05:36.2 (47초)**
  > "속기 쉬울 만큼 그럴듯해요. 프롬프트 몇 개, PRD 하나만 써도 UI가 금방 나오고, 돌아가는 것처럼 보이는 게 생기죠. 그런데 뒤에서는 덕트 테이프로 붙여 놓은 상태일 수도 있어요. 그게 70% 문제예요. AI는 앱이나 기능 코드의 70% 정도를 빠르게 만들어 내요. 뼈대, 뻔한 패턴들이요. 하지만 나머지 30% — 추가로 디버깅해야 하는 예외 상황, 실제 운영 시스템과의 연결, 인증 · 보안 · API 키가 제대로 돼 있는지 — 는 예전만큼 시간이 걸릴 수 있어요."
- 근거 (25초): **90-90 법칙**(Tom Cargill, 벨 연구소, 1985 Jon Bentley 칼럼에 소개) "앞 90%가 시간의 90%, 남은 10%가 또 다른 90%". 70% 문제는 새 현상이 아니라 **앞부분만 싸진 것**.
- 해설 (15초): 남은 30%가 예전만큼 걸린다면, 왜 사람들은 그 30%를 하지 않고 떠날까?

## ② 내 코드가 아니다
- 해설 (15초): 30%를 하려면 코드 안으로 들어가야 한다. 그런데 그 코드는 내가 쓴 게 아니다.
- **원본 C2 · 06:57.8–07:39.6 (42초)**
  > "프롬프트로 겹겹이 쌓기만 하면, 언젠가는 문제에 부딪혀요. 저도 많이 겪었어요. 어떤 최신 모델, 어떤 최신 도구를 써도 AI가 고쳐 주지 못하는 문제가 생기고, 그러면 소매를 걷고 직접 코드에 들어가야 해요. 그런데 무엇이 만들어졌는지 — 구조, AI가 내린 결정 — 를 모르면 힘들어져요. AI에게 하나를 시켰는데 다섯 군데 코드를 다시 썼다면, 뭐가 어떻게 돌아가고 어떻게 이어지는지 전혀 모르게 되죠."
- 근거 (35초): **이해 부채**(comprehension debt) — 코드 양과 내가 이해한 양의 차이. 고칠 때 한꺼번에 청구된다(arXiv 2604.13277, Addy Osmani 블로그). 덧붙여 **MIT 「Your Brain on ChatGPT」**(2025-06, 54명, 동료 심사 전): LLM으로 글을 쓴 그룹은 방금 쓴 자기 글을 인용하지 못했고, 자기 글이라는 느낌이 가장 낮았다.
- 해설 (10초): 모르는 코드를 고치면 무슨 일이 생길까?

## ③ 고칠수록 깨진다
- **원본 C3 · 07:53.7–08:26.5 (33초)**
  > "그중 하나가 '두 걸음 뒤로' 패턴이에요. 좋아하는 도구로 MVP를 만들고 기분이 좋죠. 프롬프트를 두세 개 더 던져요. 그러면 보통 이렇게 돼요. 버그 하나를 고치려 하면 AI가 그럴듯한 수정을 제안해요. IDE에 계획까지 보여 주죠. 그 수정이 다른 걸 깨요. 그걸 고쳐 달라고 하면 문제가 두 개 더 생겨요. 반복. 가끔은 새 문제가 다섯 개예요."
- 근거 (40초): 이 루프에는 이름이 여럿 있다 — **둠 루프**, 고치면-깨지고-되돌리는 루프, **둠프롬프팅**(CIO). 원인 하나는 **컨텍스트 부패**(context rot): 대화가 길어질수록 앞에서 정한 것을 놓친다(Chroma 2025, 모델 18개 측정). 직접 재현 후보: 같은 앱에 수정 요청을 10번 이어서 보내고, 매번 깨진 테스트 수를 센다.
- 해설 (10초): 이쯤에서 대부분은 고치지 않는다. 새 폴더를 연다.

## ④ 다시 시작이 싸다
- 해설 (15초): 새로 시작하면 다시 첫날의 마법이 온다. Addy는 "10배 빨라졌다"는 주장을 이렇게 본다.
- **원본 C4 · 16:22.5–16:51.7 (29초)**
  > "들여다보면, 대부분 완전히 새로 시작하는 그린필드 개발을 하는 회사들이에요. 기술 부채도, 실제로 오래 운영된 소프트웨어에 따라오는 짐도 없어요. 처음부터 만들면 처음엔 복잡한 게 별로 없으니까요. 그래서 아주 잘하고 있다고 느끼는 거죠."
- 근거 (40초): 같은 원리가 개인에게도 — **만들고-버리는 루프**(build-abandon loop): 새 프로젝트는 비용이 거의 0이고 AI는 빈 판에서 가장 잘한다. 진척처럼 보이지만 진척이 아니다. 반대편 고전: **Joel Spolsky 「Things You Should Never Do」(2000)** — 다시 쓰면 쌓인 지식(고친 버그들)을 버린다. 국내 사례: "3일 만에 폴더 삭제" 반복(GeekNews).
- 내 사례 (20초): 이 영상을 만들면서 형식을 네 번 갈아엎었다(001 기록). 매번 "새 형식이 더 낫다"는 느낌이었다.
